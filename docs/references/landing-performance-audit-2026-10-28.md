## Actual critical path

The landing creates its own procedural room, not a downloaded GLTF. Its code originally loaded only after hydration, generated complete procedural fallback pixels, fetched/decoded eight photographed material images serially, prepared a reflection environment/uploaded textures/compiled shaders/warmed the first shadowed render, then revealed155drawing calls over an800ms fade with a concurrent1100ms lift/scale entrance.

Current source prerenders the inert Canvas wrapper and lets Next emit preload hints. Production build HTML actually contains one inert canvas, nine script elements and six script preload links; this is build markup evidence, not a production network benchmark. Exact-part furniture instancing plus the bed/bedside start yields47initial calls; the fully furnished first chapter yields62. Four local image jobs replace the serial queue. The loader can reserve final-size neutral buffers and generate original procedural pixels only if photographic loading fails, before any visible GPU render. It retains the original fallback, validation/byte/pixel/fragment bounds,10second deadline and retirement. Earlier instrumentation measured resource construction304.5ms versus23.8–30.6ms after removing wasted pattern generation; that temporary render-time instrument was subsequently removed to preserve React purity.

The final audit refinement overlaps the independent image job with environment setup and asynchronous shader compilation. All material/map identities and dimensions already exist; the reflection environment is prepared before compilation as Three requires. Both jobs must settle successfully before final pixel upload, the first real render and readiness. Retirement is checked both before scheduling and inside the queued jobs, so immediate cleanup cannot start late work. A failed job never reveals the room or uploads while the other job is unresolved. This removes serial waiting while preserving actual graphics readiness. [Three WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html).

The final production root's unique linked script/preload set is14files,1866119raw bytes/540678estimated gzip bytes, below the standing700KiB estimate target. This is an offline calculation of HTML-linked files, excluding images and any unobserved lazy graph, not measured transfer/LCP. Root-layout inspection finds no editor/CPQ controller import; its verification owner renders nothing until an actual challenge is pending. Thus neither a provider request nor the challenge's12second failure timer blocks the landing.

Before the cache follow-up, three comparable1366×768 warm-asset development reloads observed readiness2612/2831/2362ms before BO versus804/753/777ms after the work above. The corresponding final internal texture/GPU preparation was333.9/306.2/299.8ms. These include measurement/tool overhead and do not establish physical cold-network, LCP/INP or hosted performance. A separately recorded immediate post-build tail was5997/2591/2239ms; it is retained rather than omitted from the claim. Later repeat measurements returned to the subsecond range without source changes. No universal subsecond guarantee is made.

## Cache finding and selected correction

Actual local HEAD requests before the cache follow-up returned `public, max-age=0` plus ETag for floor-detail and wood-normal. The root document returned no-store in development. The pinned Next16.4.2 public-folder guide confirms that ordinary public files default to revalidation; hashed `/_next/static` output gets long-lived immutable caching in production, while development chunks stay revalidatable. An old indexed Next14 snippet suggested a different default, so the pinned documentation/source and actual headers take precedence. Custom headers for eligible responses are supported by [Next headers](https://nextjs.org/docs/app/api-reference/config/next-config-js/headers).

Two source changes are selected:

1. Cache-Control `public, max-age=31536000, immutable` is restricted to the eight exact `/surfaces/{floor,wood,fabric,plaster}-{detail,normal}-v1.png` paths. These prepared files are already pinned by byte/hash/licence gates and the release policy forbids replacing a public path with different bytes. A changed material must use a new versioned URL; HTML, API, metadata/manifests, unversioned images and framework development chunks are untouched. Cache busting requires a new URL when bytes change. [MDN Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control), [existing release policy](../operations/stale-client.md).
2. The landing alone selects fetch `cache:force-cache` for this fixed allow-list. The browser can reuse stored bytes across documents/revisits, falling back to network on a cache miss. Every returned byte stream still goes through existing type/dimension/orientation/byte/fragment/decode validation, cancellation and fallback. Shared editor/export callers retain their default request policy. `force-cache` can reuse an existing stale response, so the immutable URL invariant is required. [MDN Request.cache](https://developer.mozilla.org/en-US/docs/Web/API/Request/cache).

This is browser HTTP caching of public static material bytes. It does not put guest rooms, original photos, chats, provider responses, tokens, grants, source identity or live GPU objects into persistent storage. A user may clear cache, the browser may evict it, and a cache-disabled/hard-reload workflow can still incur loading. No offline availability or permanent storage guarantee is made. Development-only diagnostics count same-origin public material Resource Timing entries with zero transfer size and a nonzero encoded body; actual cache/header and repeat-visit results belong to the receipt.

Actual local verification now confirms all eight paths return the selected one-year immutable header while root HTML and GET config retain no-store; mode remains fake/simulation. Three real refreshes report8/8material cache hits and readiness803/795/820ms. This verifies cache reuse and avoids asset downloads, **not** a further warm-local latency improvement over the earlier804/753/777ms sample. The cache is especially relevant to bandwidth/remote repeat visits; actual remote-network performance is still unmeasured.

An effect-owned profile before the final overlap refinement reports197.5ms critical material preparation and110.3ms sequential GPU preparation. GPU wall portions are39.9ms environment/texture upload,56.3ms asynchronous compilation and13.7ms first warm-render submission. Summed material-job portions are677ms fetch/body delivery,1ms validation,68.4ms native decode and7.9ms channel unpack; parallel job totals overlap and must not be added to critical wall time or called CPU/GPU execution time. This rules out header parsing/channel unpack as major current costs and shows that HTTP cache hits still have an asynchronous browser read/processing path. A persistent decoded-pixel cache could avoid more of that path, but it would add multi-megabyte storage/copy/corruption/expiry/failure ownership; no unmeasured extra storage subsystem is selected here.

After overlapping images and environment/shaders, three warm cached reloads observe862/754/768ms readiness and259.1/255.1/258.8ms internal preparation, with8/8cache hits and the same47calls/5geometries/21textures. Median internal preparation is258.8ms versus303.5ms in the preceding cached sample (about15% lower); total observed median803→768ms changes about4%, within a variable local pipeline. Current `texturesMs` includes image-job wall time; `gpuMs` sums environment/upload/compile/warm wall portions that now overlap it, so these counters must not be added. Actual first-context graphics work remains prepared before visibility. Raw samples are in `roomedy-startup-overlap.json`; no universal latency guarantee is inferred.

## Other techniques evaluated

| Technique | Fit and disposition |
| --- | --- |
| Three.Cache/FileLoader or R3F useLoader caching | Our finite validated loader uses its own fetch/decode, not FileLoader/useLoader. Three.Cache is an in-memory dictionary; enabling it would neither cover this path nor persist a refreshed document. Keep existing ownership and use browser HTTP caching for bytes. [Three Cache](https://threejs.org/docs/pages/Cache.html), [FileLoader](https://threejs.org/docs/pages/FileLoader.html) |
| Reusing GPU objects/renderers across refresh | A new document creates a new canvas/context. Existing texture/program objects belong to their renderer and are disposed with it. Do not retain detached canvases or promise cross-document GPU-object reuse; browser/driver internals may cache independently. Shader warm-up remains necessary in the new context |
| Keeping the landing canvas alive in the studio | Would add a second renderer and break the established0/1canvas phase/lifetime contract. Preserve actual route cleanup and shared editor authority |
| Shared geometry/materials and instancing | Applied within each landing canvas, preserving every authored part/material role. New instance buffers have a separate cleanup owner; geometry/materials remain borrowed. Fewer submissions improve both initial and full-room frames. [R3F scaling performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance) |
| Demand rendering/DPR limits | Already present: `frameloop=demand`, explicit invalidation while moving, sleep at rest,≤1.5DPR and≤2million backing pixels. Preserve them; do not lower visible quality or freeze active animation. [R3F scaling performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance) |
| Development versus production | Keep React strict checks and Next development chunk revalidation. Disabling them would make a local benchmark look faster while masking ordinary development behavior. Static production build/preload/header evidence is recorded separately; no production GPU/cold-load measurement is inferred |
| Explicit texture preload hints | HTML `as=fetch` hints could start the eight material reads before scene hydration, provided CORS/credentials match the eventual validated fetch. Framework script preloading is already selected. Additional high-priority texture hints are a future cold-network experiment: they may compete with critical scripts, and neither that contention nor a cold-network win was measured here. No speculative eight-request priority burst is added. [MDN preload](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/rel/preload) |
| More parallelism | Eight simultaneous image requests were measured slower than four on this local path. Keep four active image jobs, one owner/deadline and no retry |
| Overlap independent preparation | Applied: fixed texture/material structure allows image loading alongside environment/shader preparation. Both jobs settle before final upload/warm/readiness, with retirement/failure fences. This avoids serial wall time without retaining GPU objects or introducing persistent decoded storage |
| Persistent decoded-pixel IndexedDB/Cache API store | Could avoid some decode work, but adds storage failures, validation/versioning, copies and retained decoded memory. First measure native HTTP cache hits; do not add a second persistent storage system without a measured remaining decode bottleneck |
| Service worker/offline cache | Adds install/update/activation/stale-client lifecycle and a broader fetch owner without a demonstrated need. Native HTTP caching already serves the selected repeat-visit task; no service worker or API interception |
| KTX2/Basis GPU texture compression | Potentially useful for larger material sets, but current files are256/512px,912545encoded bytes total with11010048nominal texture/mipmap bytes. A transcoder adds JS/WASM startup and an asset pipeline change. Retain exact photographic quality until real network/VRAM evidence justifies that tradeoff |
| Draco/Meshopt/GLTF preloading | The landing's furniture is procedural and shares five actual geometries. There is no landing GLTF download to compress; adding a decoder would not target the measured bottleneck |
| Worker-based texture processing | Native createImageBitmap/OffscreenCanvas preparation is already used. Wasteful fallback generation was removed rather than moved to another worker. Extra worker bootstrap/copies are not selected without a measured remaining CPU bottleneck |
| Progressive low-resolution materials or cheaper glass/shadows | Could show a different first image, but risks quality swaps, new compilation and the owner's previously reported stutter/glass regressions. Staged furniture and exact-part instancing reduce work without removing material/light/shadow quality |
| CDN/hosted cache changes | A future release can benefit from static headers; no CDN/cloud/domain/deployment action is authorized or performed. Current hosted release remains unchanged |
