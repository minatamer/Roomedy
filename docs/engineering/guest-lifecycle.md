## Fixed lifetime and storage choice

The client guest session starts when its entry owner creates the controller. Its original creation time plus exactly7,200,000ms determines expiry. Accepting reviewed semantics, manual edits, assistant Apply, Undo, comparison and refresh do not extend it. An explicit new-room reset or validated import starts a fresh identity/history/lifetime. Restore preserves the original creation/expiry and creates fresh operational identity, never old commands or grants.

One `sessionStorage` key, `roomedy:workspace:v1`, belongs to the current browser tab's storage area. There is no localStorage room, server room database, cross-tab broadcast or permanent photo library. A250ms timer coalesces accepted semantic changes; selection/chat/camera orbit do not serialize another room. Minimal2D/3D view preference is included. Page-hide, visibility-hidden and owning entry teardown explicitly flush accepted data before transient resources are disposed.

Storage writes are synchronous and bounded, so there is no asynchronous IndexedDB transaction to outlive reset. The manager checks phase/expiry/identity before writing and generation/workspace identity afterward. A local write-ownership token prevents cleanup from an old success or failure deleting an identical newer record. Reset/import/expiry cancel the scheduled write before owned cleanup; only this exact key is removed. Denied/quota storage leaves useful memory-only editing with an export notice. When permitted, a failed update removes its stale recovery snapshot. If the browser also denies removal, Roomedy cannot promise immediate physical deletion; absolute expiry still prevents accepted use on restore. Browser eviction/crash/power loss can prevent recovery despite a prior successful write.

Fresh tabs without an opener start independently. Some browsers copy sessionStorage when a tab is duplicated/opened with an opener: that is an initial copy, then independent tab storage. Restore always creates a fresh workspace ID, so copied data grants no shared operational identity. Resetting one tab does not clear another tab's storage. Controlled copied-storage tests and actual separate-tab tests are different evidence; native browser-menu Duplicate was not operated here. Closing a tab normally ends sessionStorage, although browser session-restore behavior is browser-controlled. This feature promises best-effort tab refresh recovery within the fixed lifetime, not secure disk erasure or durable account projects.

## Failure, update and cleanup

Restore never chooses fake/live mode, model, provider availability or authorization. The assistant reads the current runtime configuration; manual-only availability remains usable after a valid cross-mode recovery. Refresh cannot replay recognition, assistant search, a proposal or Apply. Recovered UI accurately says photos/chat/Undo were not stored. Reviewing photos again is an explicit new-room flow; it cannot silently overwrite retained confirmations.

Missing lazy editor/search code or worker errors fence pending work and release operation resources. Accepted semantics remain exportable/recoverable, with an explicit Reload action and transient-loss disclosure; there is no automatic reload loop. Read-only inspection/2D fallback remains available. RM-014/019/020 own exact deployment IDs, old/new asset compatibility, rollback and actual hosted skew proof; injected local load-failure checks are not that evidence.

The controller fences identity/state before releasing operations/resources. Actual review/photo owners abort/fence decoders and revoke URLs; workers terminate once; assistant clients reject late replies; confirmation/file-reader/download resources are owned and released; component teardown releases subscriptions/timers and existing view resources with their shared GPU-cache policy. Persistence is an entry-owned subscription that survives an intentional controller reset long enough to remove the retiring record and save a new accepted room. Entry teardown flushes and disposes that subscription before disposing the controller. No global storage wipe, logging suppression or unrelated process cleanup exists.

## Timing and accessibility disposition

The selected two-hour limit cannot be disabled, adjusted or extended by ordinary editing/refresh; import/new-room creation is a deliberate new session. **WCAG2.2 SC2.2.1 is not established/met by this fixed-limit design; no essential or other exception is claimed.** Warning/export alone do not satisfy the adjustable/extension alternatives in the [W3C timing guidance](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html) (checked18October2026).
