## Authority and data flow

`resolveAssistantTask` is application policy shared by browser and backend. It resolves supported wording/selected controls to a conservative action/target/add/replace/remove scope at a captured room revision. The model cannot choose or enlarge that scope. True ambiguity, negation, conflicting instructions, repeated additions and unsupported wording receive a useful clarification rather than inferred permission. An unlocked object alone is not authorized.

One transient `AssistantController` owns bounded conversation and unsent draft text. The existing `SessionController` owns the canonical room, candidate projection, generation/operation identity, resource cancellation, command envelopes, receipts and whole-change Undo. There is no second scene/history authority. Selection, camera, cards, Apply, Cancel and Undo send no provider request.

An explicit request resolves locally, captures one operation token and cancels the previous candidate/work. Cheap ambiguity/unsupported/visitor-control/Undo guidance stays local. Already-selected finishes need no search/provider call. A layout goal runs the actual browser worker using the existing bounded search; only its action candidate is untrusted input to the backend. The backend independently re-resolves scope and rechecks geometry, goal satisfaction, offered variants and computed facts. It can run the same yielding backend search if no worker candidate is supplied. Direct application-resolved left/right/removal batches need no model round, but still pass shared preparation.

The source-controlled `grounded-room-2` prompt treats visitor text, labels, history and tool results as untrusted data. One user context item contains current semantic room/provenance, selection, resolved task/scope, offered catalogue options and bounded recent text. No photos, private filenames, grants, keys, old tool payloads or raw provider prose are attached. For an application-resolved task, final model output is only `{kind:"done"}`; actual reply copy, checks, measurements and receipts belong to the application. For otherwise unresolved safe language, one strict design-intent call can select only a closed goal, current furniture IDs, supported categories/finish/palette. It has no tools, actions, measurements, coordinates or arbitrary prose. Application-authored clarification choices name the concrete new request; this interpretation cannot prepare edits. Choosing a current choice starts a fresh ordinary request, independently compiled at both ends.

## Supported capabilities and boundaries

| Capability | Actual behavior |
| --- | --- |
| Work area by window | One desk and at most one chair; disclose both affected pieces. Other furniture/finishes stay unchanged. Multiple desks/chairs/windows require actual selection/clarification. |
| Rearrange owned / clear entrance | Only owned movable targets; fixed pieces remain fixed. Entrance requests use computed entrance blockers rather than authorizing all unlocked pieces. No additions/replacements. |
| Furnish / add essentials | One of each named supported category; stable application IDs. Kept/nearby nouns are not additions. Existing furniture is not resized or moved to manufacture room. |
| Remove / replace | One explicit target; independent starting locks and retained/owned preference must permit it. Replacement is a supported proposed representation, distinct from measured owned size. |
| Left/right move | Known physical extent and room width; retain orientation/depth position and unrelated pieces. A rotated unknown footprint requests its actual dependent depth. |
| Room/piece appearance | Three supported room directions or a selected supported piece finish. Preserve geometry; owned finish is unchanged by general room presets. Proposed eligible finishes are part of the captured batch. |
| Explain/check/focus | Source-controlled facts and canonical IDs. Unknown or approximate checks stay visibly incomplete/approximate. Cards focus the real item/field. |
| Visitor controls | Missing measurement, independent lock, replacement preference and explicit Undo guidance point to real controls. Tools never confirm a value or unlock a piece. |
| Unsupported request | Prices, budgets, shopping and unknown finishes/capabilities receive concise size/layout/style alternatives. No retailer, URL, code or arbitrary network tool exists. |

Mixed add/move/finish batches and coordinated swaps are atomic when explicitly scoped by application preparation. Free wording that cannot safely establish all targets asks for narrower choices; it does not silently authorize a broader batch. Common design requests and bounded follow-ups are compiled before exact preparation; unresolved language can use the strict interpretation/clarification path. Actual live-model quality remains unverified.

## Strict tools and bounded execution

Closed contracts allow `read_room`, `find_furniture`, `find_arrangements`, `prepare_edits`, `explain_checks`, `focus_item`, `request_measurement`, `request_lock_change` and `request_undo`. Each resolved task exposes only its relevant subset. Full furniture entities, dimensions/ownership/provenance and add/replace variants are built by application code from approved catalogue choices; flat tool arguments cannot fabricate them. Irrelevant non-null fields, extra properties, unknown tools/IDs/variants, unlock/confirmation and out-of-scope edits reject.

The serial loop allows at most4 provider rounds and the existing16-tool ceiling, with one call per round, deduplicated call IDs, strict projected schemas and no retry. A final output without a computed decision is incomplete. Repeated distinct prepared batches reject. Known spatial/lock rejection returns the actual computed issue, not a successful fit claim. Goal/preset fidelity is checked in addition to generic schema/space compliance. Measurement requests must be missing dependencies in actual unassessed checks relevant to the selected task; another piece's width may legitimately matter to a selected piece's overlap check.

The shared finite runtime/admission controls remain unchanged:60s assistant operation,45s provider call,110s independent browser watchdog, byte/fragment/token/rate/grant/concurrency bounds and real-settlement slot retention. Stateless `store:false` reasoning/function-call replay stays in bounded operation-local backend memory; see [transport policy](provider-safety.md). Browser history is at most80 compact messages/256KiB, with at most40 recent text turns/64KiB supplied to a request. Stored cards drop actions and retain at most8 objects/issues/fact IDs. No refresh replays an operation.

## RM-015F conversational design layer

A pure language layer recognizes requests for less cramped circulation, daylight/work-area improvements, coherent/cozy/light/calm finishes, explicit quarter-turn rotation and user follow-ups. Current named targets take precedence over selection; selected or unambiguous prior user references can resolve a finish/side/rotation correction. Only the latest bounded user turn supplies a reference; assistant prose cannot grant permission and no old add/remove/replace authority is inherited. Ambiguous/missing targets ask one grounded question. Explicit contradictory/negated instructions remain conservative. Supported “without moving” exclusions fix the named IDs; targeted/only-piece open-space requests do not authorize unrelated unlocked furniture.

`open-space` extends the existing bounded optimizer to eligible owned or proposed existing pieces. The narrower rearrange-owned contract still excludes proposed furniture. Both goals require increased modeled central free area or computed hard-issue repair. Locks/exclusions, unknown dimensions, geometry, catalogue policy and final-batch validation remain unchanged. Open-space never adds/removes/replaces. Work goals coordinate the actual desk/chair pair. Layout plus an explicit palette uses the existing extraFinish mechanism in one final batch; complete final facts include the room palette change. Replies describe actual mm/m² comparisons and supported color choices without inventing a fit guarantee.

Palettes are warm oak/clay, light oak/ivory and calm walnut/sage. General palettes preserve owned finishes. An explicitly requested owned-piece finish is now passed by the validated scoped entry point into the same command authority at preparation and Apply; bare/unscoped assistant batches retain their previous owned-finish protection. Supported finish eligibility remains strict and unrelated targets, dimensions, ownership and locks cannot change. This corrects the old resolver/authority mismatch where a selected owned finish was understood but every such candidate was rejected.

Clarification replies have at most3 optional choices; label/request sizes remain finite and choices include the input room revision. Only the actual latest message's owned choice can be selected; a changed revision, Before, expiry or fabricated choice cannot trigger it. Old choice buttons disable. Context is captured before the current message is appended, bounded identically at frontend/backend by40 turns/64KiB; it is transient, never recovered/exported. The strict interpretation call uses existing admission, serial/deadline/byte limits and no retry. Fake has an authored clarification branch; G owns expanded story/protocol parity evidence. [F execution/validation](../validation/RM-015F.md) distinguishes injected Responses protocol from actual live-model evidence.

## RM-015G sample interpretation and parity

The offline adapter now parses bounded supplied context and authors strict intents for unfamiliar circulation/style/furnishing wording, bound to actual current or unambiguous recent user references. It verifies selected IDs/categories/offered finishes; ambiguous/missing targets stay clarification. It returns only offered tool names for normal tasks. No fake branch invents actions, observed measurements or a successful room from an unrelated fixture. Authored vocabulary is not live-model interpretation evidence.

Clarification policy is shared with real interpretation: empty rooms can offer an explicit essentials request; layout options need movable furniture and work-by-window needs a real desk/window. Unsupported piece finishes do not become misleading options. Choosing a piece-specific option retains the assistant panel/composer. Runtime mode, capability/funding/admission and transport are unchanged; the repeated fake-mode banner is removed.

`assistantSearchFallback` is one application-owned constructor shared by frontend/backend. Otherwise no-candidate retains unchanged room/history and a separately chosen palette or catalogue/size alternative. It never claims global impossibility or successful fit, auto-retries, widens targets, changes unknown evidence or raises limits.
