## Media policy and ownership

The byte-only codec/manifest/draft contract lives in `@roomedy/contracts/intake`, shared with later server admission. Browser-native bitmap/canvas work stays in `features/room-intake/images.ts`; the backend never imports a frontend decoder. Selection makes no provider request. The disabled photo-draft action states current unavailability; a fully useful manual path remains available. JPEG/PNG/WebP are explicitly supported still rasters; GIF, SVG, HEIC, animated PNG/WebP, PDFs/native scans/remote URLs and 16-bit PNG/non-8-bit JPEG are unsupported. Export guidance is contextual; broad phone/device compatibility is unverified.

Count/bytes/pixels are independent: 6 selected files, 8 MiB each / 24 MiB selected-plus-retired-active raw bytes, 16 million pixels and 8000 px per edge. Header scanning caps at 4096 segments/chunks. Real signatures and header dimensions precede native decode; MIME/extensions are not trusted. The sanitizer removes ancillary metadata/profiles/text before decoding and preserves only a bounded EXIF orientation scalar. It bounds segment/offset work and keeps approved image chunks/scan data. Valid native decode must match preflight dimensions. Embedded profiles are intentionally removed; exact wide-gamut colour reproduction is not promised.

One native job runs at a time, with a 15-second visible deadline. A retired native promise retains its slot until it settles; abort does not pretend to force-stop browser codec internals. Late bitmaps are closed and stale output cannot publish. Native/driver RSS or an absolute process memory ceiling is not established by an application deadline. File buffers, sanitized copies, canvas size, selected/retired records and output blobs remain separately bounded. At 16 MP, RGBA output alone can require 64 million bytes; a 2048-square canvas about16.8 million. A 640-edge preview avoids six retained full-size image decodes. Actual native intermediates, heap/driver allocation and GC timing remain unmeasured.

Normalization draws the explicit orientation once, fills transparency with warm paper and produces JPEG at at most2048 px per edge. At most three quality attempts (.82/.65/.5) must fit2 MiB each, with6 MiB normalized total. Preview JPEGs are at most640 px /256 KiB. Prepared Base64/framing ceilings remain separate (6 MiB bytes becomes8 MiB Base64 within a10 MiB prepared-request cap). The future provider request is an allow-listed manifest plus normalized blobs, without filenames or operational handles. Server enforcement belongs to RM-008; client policy is not server authorization.

Original File/byte/bitmap references are released after preparation. Only normalized in-memory images and small local previews remain while review needs them. PhotoStore owns preview URLs, one active job and six selected records; an additional retired native job is counted in raw admission until settlement. Remove/unmount/expiry fences before releasing URLs/buffers. Replacing a photo is deliberately two-step: add/check its replacement before removing the old preview; if six slots are already occupied, remove an expendable photo first. Invalid additions preserve existing work. Photo reorder preserves opaque IDs. No photos, blob URLs, decoder handles or prepared bodies enter accepted semantics, storage or export. On explicit studio entry, remaining previews are released, as disclosed next to acceptance.
