### SEC-001 — Unfinished request bodies strand the public AI bridge's slots

**Threat:** denial of service. **Affected owner:** `apps/frontend/src/server/bridge-post.ts:30–52,91–123,199–208`. This applies to public mutation intake before schema/challenge/grant/provider work. Manual editing and ordinary page/health GETs remain available. Next can create separate loaded route pools; the demonstrated admission pool is necessary for fresh AI operations, so exhausting it blocks those operations regardless of other pools.

`active` increments before reading the request. The reader checks the abort signal only after `await reader.read()` returns. The body deadline aborts a controller and resolves the visible response, but no abort listener cancels the owned input reader. The `active--` cleanup belongs to the still-waiting raw promise. An attacker can leave the stream unfinished; merely returning408/504 does not establish reader settlement or release the slots. Server-side Origin/release checks do not prevent a custom client from supplying their public values, and Turnstile is reached only after input parsing.

**Actual reproduction:** against the exact frontend image, in a temporary no-network container, send two loopback POSTs to `/api/roomedy/v1/admission`, with correct public origin/release, JSON type, Content-Length1024 and only the first `{` byte. Both return408 at the real15second intake deadline. A later complete `{}` request returns429 instead of reaching400 schema validation. After both original clients are destroyed and a200ms settling interval, another complete request still returns429. No backend service, proof token, secret read or upstream/provider call is involved. Owned container cleanup completes. Separate injected-stream reproduction returns two504 responses then429, with zero input-stream cancellations and zero upstream fetches. Equal accelerated timers in that injected case explain504; the native result uses the unchanged real15second timer.

**Impact/limits:** a small number of unfinished requests can deny fresh AI admission on a process despite visible timeouts and client disconnect. The observed retained counter survives those disconnects; no long-duration production persistence or multi-instance exploit was performed. The actual code has no independent retirement path for that pending read. Restart may recover availability but is not the correction. A larger instance count only multiplies the attacked pools and can increase cost.

**Smallest safe plan:** bind cancellation to the owned stream reader as soon as it is acquired; abort/deadline must promptly retire pending input reads, cancel the owned stream, clear packed memory/listeners and release input ownership exactly once. Distinguish local untrusted body ownership from an already-dispatched unresolved upstream operation: retain the existing conservative upstream slot policy until actual settlement. Do not simply decrement `active` when the visible timeout wins, remove admission limits, add automatic retries/restarts or raise concurrency. Keep all byte/fragment/content-type/schema/origin/release checks and fixed safe errors.

**Execution allocation after selection:** existing bridge owner and `test/bridge-post.test.ts`, security disposition/receipt, current ticket/progress and exact RM-018 file plan. Reuse existing cancellation primitives; no dependency/service/port/framework change. Add a regression with stalled input that confirms cancel/retirement and subsequent valid intake; cover caller abort, timeout, late chunk, fragment overflow and exactly-once cleanup. Retain the current abort-ignoring-upstream test unchanged in meaning. Run focused bridge/lifecycle/admission checks, required settled gates and current image proof; repeat the same bounded native two-stream case and show later input reaches validation/normal admission. Refresh release input/image identity before deployment. No implementation is included in this report.

### SEC-002 — Paid activation has no verified account-wide funded cutoff

**Threat:** resource/cost abuse; conditional on public paid activation. **Evidence:** `packages/contracts/src/policy.ts:51,66–77`; `apps/backend/src/security/admission.ts:79–100,119–175`; `apps/backend/src/runtime/operations.ts`; current operations/runbooks and owner's report of a configured budget alert. The four Secret Manager records have enabled version1 metadata; no secret value or provider account funding configuration was read.

The code correctly limits each process to30 admissions/12 admitted operations per60seconds, two expensive operations, at most four serial provider rounds and8192 output tokens per call. It has no hidden retry, and it rejects stale/replayed grants. Those are useful finite work controls. They do not cap spending over a day/lifetime, survive a restart as a shared spend ledger, or coordinate overlapping revisions/instances. Turnstile reduces automated abuse but is not a monetary quota or identity. A Google Cloud billing budget is an alerting mechanism, not an automatic spending ceiling; it also does not itself cap charges on a separate provider account. [Google's budget documentation](https://docs.cloud.google.com/billing/docs/how-to/budgets).

**Impact/limits:** a legitimate or abusive client that obtains repeated verification can keep using metered operations over time; overlap/restart can multiply independent process allowances. Whether the current OpenAI account already has a sufficiently enforced funded boundary is **unknown**. This is not a demonstrated overspend or a claim that billing is misconfigured. Paid-off startup already prevents provider composition/dispatch, so a correctly verified paid-off release can be considered independently of this finding.

**Smallest safe plan:** leave `PAID_DEMO_ENABLED=false` for first hosted verification while domain/challenge setup is deferred. Before public paid activation, verify and document the actual provider funding mechanism's enforcement and accepted maximum outstanding exposure; do not substitute a soft monthly project budget, a Google alert or maxInstances1 for that evidence. Prefer an existing enforceable account mechanism over building a new database/quota service for this demo. Keep the paid-off operational switch and bounded local policy. If no enforceable external bound is available, return the concrete tradeoff for a selected narrowly scoped remedy; do not invent or implement one during this audit.

**Verification after selection:** content-free hosted readiness confirms live/disabled and no metered dispatch with paid off. Record effective Cloud Run instance/revision/concurrency/timeout settings and actual account-control evidence without copying credentials or making unapproved paid requests. Test any selected local correction with fake injected providers first. Paid activation remains separate from secret existence and hostname registration. No external account setting or runtime configuration is changed here.
