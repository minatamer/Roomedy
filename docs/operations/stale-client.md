# Already-open clients and compatible assets

18 October2026. The selected policy combines a content-derived release ID, explicit API agreement, immutable compatible asset retention and visitor-controlled reload. It does **not** configure Next`deploymentId`: its documented hard-navigation behavior can discard transient photos/drafts. `generateBuildId` uses the release ID; client/server API guards carry the same public comparison value. This value never selects fake/live mode, authorizes a command, confirms dimensions or grants paid work. [Next self-hosting/version skew](https://nextjs.org/docs/app/guides/self-hosting#version-skew), [standalone output](https://nextjs.org/docs/app/api-reference/config/next-config-js/output).

Normal image builds use the exact source+retained-public-input digest as release ID. Ordinary development and non-release host builds may omit it; that does not qualify as strict release evidence. The A/B native experiment uses explicit64character test identities (`a…a`/`b…b`) for isolated outputs, **not claimed content-derived image proof**. Production app values are generated by the release builder and verified against image labels/inputs before acceptance.

Every versioned AI client request sends`X-Roomedy-Release`. The frontend rejects missing/mismatched mutation identity **before** identity acquisition, upstream parsing/admission or provider work. Responses carry the server release ID. A mismatched/missing response identity prevents its body reaching client operation decoding. Main-editor mismatch fences pending work/candidate/Apply through the canonical controller, preserves exportable accepted current/baseline data and shows explicit Reload with transient-data warning. It does not replay/retry or automatically reload. Fixed session expiry still applies. Backend independently rejects frontend/backend release disagreement before grant/work; content-free GET health remains accessible inside its private platform boundary.

During photo intake, a version mismatch ends only that draft operation. The current in-memory sketch, reviewed values and selected photos stay available for manual continuation. The message states that photos/drafts cannot recover after reload. Do not call the main-editor cleanup path there: it would dispose the transient PhotoStore. Reload is a visitor choice. A framework navigation/browser failure can still discard transient state; pagehide best-effort recovery covers accepted semantic data only. No durable photo or draft recovery is claimed.

Retain the old frontend's actual `.next/static` chunks (including lazy cutaway and worker), public catalogue/models/thumbnails/fonts and current assets for at least120minutes+10minute grace after last old-revision traffic. The helper verifies raw hashes and an owned snapshot's age, copies only bounded public/static files, rejects source/env/key/symlink canaries and rejects differing bytes at an existing path. Rename/version a changed asset; never silently overwrite it. A long deployment needs a refreshed snapshot/retention decision. Source and retained bytes participate separately in exact inventory, together in release identity. Retained manifests are provenance, not public runtime files.

Schema/catalogue/rules validation is independent of release identity. Wrong versions reject rather than implicitly migrate or copy old grants/candidates/history. Lazy chunk or worker load errors fence pending editing and keep accepted export/recovery where available; they do not create reload loops. The existing cutaway provides a2D fallback when a rendering/asset capability is unavailable. Actual version/load failures and unsupported physical geometry are distinct from provider interpretation errors. A missing chunk is not a reason to relax command/schema/spatial rules.

Rollback restores a named compatible frontend/backend pair and compatible assets. Existing process-bound grants remain retired; only a visitor's new explicit request may seek a new grant. After explicit reload, compatible unexpired accepted semantics may restore with the original fixed deadline, new operational IDs and empty history. Transient photo/draft/chat/candidate state has no such promise. A release/settings record in imported/recovered JSON never changes runtime mode or availability.

The local A/B experiment, controlled version/rollback tests and final exact candidate are recorded in [RM-014 validation](../validation/RM-014.md). Windows production-browser behavior is separate from Linux runtime, hosted traffic routing, real IAM, actual model quality and physical-device evidence. RM-019 must refresh image/runtime proof after RM-015/016/018 changes; prior A/B screenshots are historical observations, not an evergreen pass.
